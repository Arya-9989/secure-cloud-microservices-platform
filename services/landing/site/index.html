Architecture

One way in.

Traefik is the only published entry point. The services and PostgreSQL sit on an internal Docker network with no route to the internet, and metrics and health ports are never routed through the gateway.

Follow one request.

  1. 1

    Log in.

    POST /api/v1/auth/token/

    Email and password pass through the gateway, which allows auth routes 10 requests a second per IP, to auth-service, which throttles again per IP and per account.

  2. 2

    RS256 token issued.

    200 · access_token · refresh_token

    auth-service signs a 15-minute access token with its private RSA key. The token’s kid header names the key by its RFC 7638 thumbprint.

  3. 3

    JWKS fetched.

    GET /.well-known/jwks.json

    The client calls orders-service with the bearer token. With no keys cached yet, orders-service fetches the key set from auth-service on the internal network and keeps it for 5 minutes. An unknown kid forces a refetch, at most two every 10 seconds.

  4. 4

    Verified at orders.

    GET /api/v1/orders · 200

    orders-service checks the signature offline, RS256 only, then iss, aud, exp and sub with 30 seconds of skew, and requires orders:read. With the keys cached, auth-service is not on this path.

  5. 5

    No token, 401.

    GET /api/v1/orders · 401

    Without a token the gateway still forwards the request, and orders-service refuses it: 401 with a WWW-Authenticate: Bearer challenge and a problem document. The live console’s last row sends exactly this request.

  • Edge

    TLS 1.2+ with AEAD ciphers and HSTS on the HTTPS entry point. Per-IP rate limits, a 1 MiB body limit, security headers, and JSON access logs with the Authorization header redacted.

  • Containers

    Services, gateway and monitoring run as non-root users on read-only root filesystems, with every capability dropped and no-new-privileges. The JVM runs on a distroless image, and the gateway never gets the Docker socket.

  • Data

    One PostgreSQL database and one least-privilege role per service. Secrets are generated locally into a git-ignored .env, and the services refuse to start without them.

Tokens

Signed once.
Verified anywhere.

auth-service signs short-lived access tokens and publishes the public keys as a JSON Web Key Set. orders-service checks every token locally against cached keys, so the identity service is never on the hot path of a read, and reads keep working through an auth-service outage for as long as the tokens are valid.

  1. 01

    Sign

    RS256 with an RSA key of at least 2048 bits, 3072 when generated locally. The private key lives in a 0600 volume or a Kubernetes Secret, never in the image. Access tokens last 15 minutes.

  2. 02

    Publish

    /.well-known/jwks.json serves the key set with max-age=300. Each kid is the key’s RFC 7638 thumbprint, so it can never drift from the key itself.

  3. 03

    Verify

    Only RS256 is accepted, so alg=none and HS256 key-confusion forgeries fail. Issuer, audience, expiry and subject are checked with 30 seconds of clock skew.

  4. 04

    Rotate

    An unknown kid triggers a JWKS refetch, at most two every 10 seconds, so orders-service picks up a new signing key without a restart and forged key IDs cannot flood auth-service. Retired public keys can stay in the set until their last tokens expire.

Sessions

Reuse is treated
as theft.

Refresh tokens are opaque, single use and stored only as SHA-256 digests. Each login starts a token family. Present a token that was already rotated, and the whole family is revoked.

  1. POST /api/v1/auth/token/

    Log in

    A new family starts and refresh token R1 is issued with a fresh access token.

  2. POST /api/v1/auth/token/refresh/

    Rotate

    Under a row lock, R1 is marked rotated and R2 is issued in the same family.

  3. POST /api/v1/auth/token/refresh/ with R1 again

    Replay detected

    Every token in the family is revoked, including R2. The caller gets 401, and the legitimate holder must sign in again.

  4. auth_refresh_token_reuse_detected_total

    Alert

    The counter increments and Prometheus fires RefreshTokenReuse.

7 days

30 days

Logging out revokes the family. Disabling an account or changing its role revokes every refresh token it holds, immediately.

Authorization

Scopes for APIs.
Roles for people.

Roles map to scopes in one table on the auth service. Resource servers authorize on scopes, and add a role check only where defence in depth is worth it.

Rate limits

Limits at every layer.

The gateway sheds floods per client IP before they reach a service. auth-service adds its own throttles per IP and per account, shared across workers and replicas through the database cache.

Gateway, auth routes
10/s
Average per client IP, burst 20.
Gateway, all other routes
50/s
Average per client IP, burst 100.
Logins per account
5/min
On top of 20 per minute per IP. Even the right password is refused while throttled.
Request body
1 MiB
The most the gateway will buffer for any request.

Sign-ups are limited to 10 per hour per IP, and refresh or logout calls to 60 per minute per IP. The local compose stack relaxes the per-IP login and sign-up limits so the test suite can run repeatedly; the per-account limit is unchanged.

Observability

Every signal,
one schema.

Both services export the same http_server_requests_seconds histogram, so one PromQL query covers Python and Java alike. Grafana opens on a provisioned dashboard.

  • Six alert rules.

    • TargetDownA target is not scraped for 1 minute.
    • HighServerErrorRateOver 5% of a service’s own responses are 5xx for 5 minutes.
    • GatewayErrorRateOver 5% of a route’s requests fail with 5xx at the gateway for 5 minutes, including a service that is down.
    • SlowRequests95th-percentile latency above 1 second for 10 minutes.
    • RefreshTokenReuseAny replay in the last 15 minutes.
    • LoginBruteForceMore than one failed or throttled login per second for 5 minutes.

  • One ID per request.

    A well-formed X-Request-ID from the client is kept; otherwise one is generated. It is echoed in the response, recorded by the gateway access log, attached to every JSON log line and included in every problem response.

Delivery

Nothing ships unscanned.

GitHub Actions runs on every push and pull request, with every action pinned to a commit SHA and least-privilege tokens per job. A Jenkinsfile runs the same stages.

  1. 1

    Lint and types

    ruff, mypy --strict, Spotless, -Werror

  2. 2

    Unit and integration

    84 pytest tests on PostgreSQL. 59 JUnit tests with Testcontainers. 11 Node tests for the live console.

  3. 3

    Audit and validate

    pip-audit on locked dependencies. kubeconform -strict on the manifests. promtool tests for every alert rule.

  4. 4

    Scan

    Trivy fails the build on any fixable HIGH or CRITICAL vulnerability in every image.

  5. 5

    End to end

    31 black-box tests against the full stack, through the gateway.

  6. 6

    Publish

    On main only: both service images go to GHCR with SBOM and provenance attestations.
